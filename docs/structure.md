# Repository structure

`vps-server-workbench` holds the tools for building and running VPS servers (DigitalOcean + Ploi today):
shell scripts that run on or against servers, Docker stacks, and PHP and Python packages for automation
that grows beyond shell. Folders are split **by language first, then by area**, so each language keeps its
own tooling (shellcheck, Composer, pyproject) and each area is easy to find. Everything is reachable through
one entry point, [`bin/workbench`](tools/cli.md).

```text
bin/          entry point: workbench (shell tools, platform APIs, Python)
shell/        Bash tools, one folder per area
  db/           DB server: docker-db-server-manager.sh (runs on the server), remote-run.sh (workstation)
  web/          web server: update-env-db.sh, check-db-reach.sh
  deploy/       ploi-deploy.sh (pasted into Ploi)
  tunnels/      workstation SSH tunnels: db-tunnel.sh
php/          Composer package simtabi/vps-server-workbench (PSR-4, namespace Simtabi\VpsServerWorkbench)
  bin/          workbench-php (the CLI behind bin/workbench do|cf|ploi|gcp)
  src/          Http (transport, retries), Safety (pending actions, audit), Security (secrets, credentials),
                DigitalOcean/ Cloudflare/ Ploi/ Gcp/ (one folder per platform), Console (CLI), Support
  tests/        PHPUnit on a mock PSR-18 client (no network)
python/       Python package vps-server-workbench (pyproject, src layout, import vps_server_workbench)
  src/ tests/
stacks/       Docker Compose stacks deployed to servers: caddy/ (the DB stack is generated by the manager)
config/       *.example templates for every tool (no secrets, ever)
docs/         index, guides (installation, getting started, configuration, architecture, security, release ...)
  tools/        one reference page per tool: DB manager, deploy script, Caddy stack, platform API, CLI, Python
  recipes/      task-based how-tos: SSH access, Ploi web server, daemons, connections, upgrades, rollouts
  adr/          architecture decision records
examples/     per-project configs (the only place a project name may appear)
tools/        standalone helpers that are not part of a server workflow (ploi-do-plan-finder)
tests/        repo-level tests: shell/ (smoke, deploy sandbox, upgrade integration), docs/ (links, Mermaid)
scripts/      compatibility shims for the old paths (see below); do not add new files here
.github/      CI workflow, issue and PR templates, Dependabot
```

The layout follows common conventions: `bin/` for executables, Composer's PSR-4 `src/` + `tests/`, the
PyPA-recommended `src/` layout (tests run against the package, not the folder), and docs split the way the
other Simtabi packages do it: guides at the top of `docs/`, one reference page per tool in `docs/tools/`,
task-based recipes in `docs/recipes/`, and decisions in `docs/adr/`. Diagrams stay inline as Mermaid in the
page they explain; `make mermaid` renders them all. Why this layout: [ADR 0002](adr/0002-layout-by-language-then-area.md).

## Where new things go

| You are adding | Put it in | Name it | Wire it into |
|---|---|---|---|
| a Bash tool | `shell/<area>/` (new area folder if none fits, e.g. `shell/ssh/`) | `kebab-case.sh`, executable, header with usage | nothing: `make lint` finds every `*.sh`; add smoke checks in `tests/shell/smoke.sh`; `bin/workbench <area> <tool>` finds it |
| a platform API call | `php/src/<Platform>/` resource method + DTO in `Data/`; a command in `php/src/Console/Application.php` | `PascalCase.php`, one class per file | a mocked test in `php/tests/Unit/` (`make php`); [platform-api.md](tools/platform-api.md), [cli.md](tools/cli.md) |
| Python automation | `python/src/vps_server_workbench/` module + a subcommand in `cli.py` | `snake_case.py` | a `test_*.py` in `python/tests/` (`make python`); [python.md](tools/python.md) |
| a Docker stack | `stacks/<name>/` with `docker-compose.yml`, `.env.example` | lower-case folder | `make compose-check` |
| a config template | `config/<tool>.env.example` | `<tool>.env.example` | the tool's docs |
| a tool reference / recipe | `docs/tools/` or `docs/recipes/` | `kebab-case.md` (recipes start with a verb) | the index in [docs/README.md](README.md); `make links` checks it |
| a decision | `docs/adr/NNNN-title.md` | next free number | the list in [adr/README.md](adr/README.md) |
| a project's values | `examples/<project>/` | as the tool expects | the project README |

Rules that do not change: no secrets in the repo, no project names outside `examples/` and `CHANGELOG.md`
(`make test` enforces it), pinned image versions, and `make ci` green before every commit.

## Old to new paths

is still installed as `/root/docker-db-server-manager.sh` with its config at `/etc/docker-db-server-manager.conf`.
